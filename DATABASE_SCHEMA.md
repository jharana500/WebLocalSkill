## Models

### `User` (`users`)
Core account. `role`, `isActive`. Relations: `profile` (1:1, job seekers), `company` (1:1), `applications`, `savedJobs`, `resume` (1:1), `passwordResets`, `reviewedVerifications` (as admin reviewer), `adminAuditLogs` (as admin actor), `notifications`.

### `Company` (`companies`)
`name`, `normalizedName` (Phase 4 — computed via `normalizeCompanyName()`, kept in sync on register/profile-update), `industry`, `size`, `phone` (Phase 4), `website`, `district`, `address`, `description`, `logoUrl`, `isVerified` (boolean, authoritative badge flag — only ever `true` when `verification.status === VERIFIED`), `status` (`CompanyStatus`), `plan`. Relations: `user` (owner, `userId` unique — one company per user), `jobs`, `verification` (1:1), `duplicateFlaggedBy` (reverse of other companies pointing here as their duplicate target).

### `CompanyVerification` (`company_verifications`)
One row per company. `panNumber`, `registrationNumber` (Phase 4 — previously collected by the frontend form but silently dropped by the backend; now persisted), `panDocumentUrl`, `registrationCertUrl`, `status` (`VerificationStatus`), `reviewNotes` (reused as the single reason/notes field for every decision type — verify/reject/duplicate/restore), `reviewedById` + `reviewedBy` (Phase 4 — which admin, not just when), `reviewedAt`, `duplicateOfCompanyId` + `duplicateOfCompany` (Phase 4), `submittedAt`.

### `AdminAuditLog` (`admin_audit_logs`) — new in Phase 4
`adminId` + `admin`, `action` (e.g. `VERIFIED`, `REJECTED`, `DUPLICATE`, `UNDER_REVIEW`, `RESTORED`), `entityType` (currently always `"Company"`), `entityId`, `oldValue`/`newValue` (JSON — `{status, isVerified}` snapshots), `reason`, `createdAt`. No `updatedAt` — audit entries are append-only.

### `Notification` (`notifications`) — new in Phase 4
`userId` + `user`, `type` (currently `"COMPANY_VERIFICATION"`), `title`, `message`, `data` (JSON, e.g. `{companyId, status, reason}`), `readAt` (nullable — unread by default), `createdAt`.

### `Job` (`jobs`)
`companyId` + `company`, `title`, `description`, `requirements`, `jobType`, `category`, `salary`, `district`, `address`, `isActive` (also doubles as the draft/published flag — see `API_CONTRACT.md`'s Jobs section), `isFeatured`, `expiresAt`. Relations: `applications`, `savedBy`.

### `Application` (`applications`)
`jobId` + `job`, `userId` + `user`, `coverLetter`, `resumeUrl`, `status`, `notes`. Unique on `[jobId, userId]`.

### `SavedJob` (`saved_jobs`)
`jobId` + `job`, `userId` + `user`. Unique on `[jobId, userId]`.

### `JobSeekerProfile` (`job_seeker_profiles`), `Education`, `Experience`, `Certification`
Standard job-seeker profile tree, one profile per user, each with its own child records.

### `Resume` (`resumes`)
One resume per user (`userId` unique). `title`, `summary`, and JSON columns (`personalData`, `experience`, `education`, `skills`, `projects`, `certifications`) — flexible-shape sections, validated/normalized at the API layer rather than the DB layer (see `resume.controller.js`).

### `PasswordReset` (`password_resets`)
`userId` + `user`, `tokenHash` (unique — the raw token is never stored), `expiresAt`, `usedAt` (nullable — single-use).
