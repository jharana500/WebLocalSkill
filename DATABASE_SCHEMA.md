## Models

### `User` (`users`)
Core account. `role`, `isActive`, `notificationPreferences` (`Json?`, Phase 5 — replaces a settings endpoint that previously echoed input back without saving it). Relations: `profile` (1:1, job seekers), `company` (1:1), `applications`, `savedJobs`, `resume` (1:1), `passwordResets`, `reviewedVerifications` (as admin reviewer), `adminAuditLogs` (as admin actor), `notifications`.

### `Company` (`companies`)
`name`, `normalizedName` (Phase 4), `tagline` (Phase 5), `industry`, `size`, `foundedYear` (Phase 5), `email` (Phase 5), `phone` (Phase 4), `website`, `district`, `address`, `description`, `logoUrl`, `isVerified` (boolean, authoritative badge flag — only ever `true` when `verification.status === VERIFIED`), `status` (`CompanyStatus`), `plan`. `tagline`/`foundedYear`/`email` were already collected by the frontend profile form before Phase 5 — the columns just didn't exist, so the values were silently discarded on every save. Relations: `user` (owner, `userId` unique — one company per user), `jobs`, `verification` (1:1), `duplicateFlaggedBy` (reverse of other companies pointing here as their duplicate target).

### `CompanyVerification` (`company_verifications`)
One row per company. `panNumber`, `registrationNumber` (Phase 4), `panDocumentUrl`, `registrationCertUrl`, `status` (`VerificationStatus`), `reviewNotes` (reused as the single reason/notes field for every decision type — verify/reject/duplicate/restore), `reviewedById` + `reviewedBy` (Phase 4), `reviewedAt`, `duplicateOfCompanyId` + `duplicateOfCompany` (Phase 4), `submittedAt`.

### `AdminAuditLog` (`admin_audit_logs`) — added in Phase 4
`adminId` + `admin`, `action` (e.g. `VERIFIED`, `REJECTED`, `DUPLICATE`, `UNDER_REVIEW`, `RESTORED`), `entityType` (currently always `"Company"`), `entityId`, `oldValue`/`newValue` (JSON — `{status, isVerified}` snapshots), `reason`, `createdAt`. No `updatedAt` — audit entries are append-only.

### `Notification` (`notifications`) — model added in Phase 4, management endpoints added in Phase 5
`userId` + `user`, `type` (`"COMPANY_VERIFICATION"` from Phase 4, `"APPLICATION_STATUS"` added in Phase 5), `title`, `message`, `data` (JSON, e.g. `{companyId, status, reason}` or `{applicationId, status}`), `readAt` (nullable — unread by default), `createdAt`. Phase 4 only ever wrote rows; Phase 5 added `GET`/mark-read/mark-all-read/`DELETE` so users can actually read and manage their own notifications.

### `Job` (`jobs`)
`companyId` + `company`, `title`, `description`, `requirements`, `benefits` (Phase 5), `jobType`, `experience` (Phase 5), `category`, `salary` (legacy free-text field, kept but no longer written by the create/edit forms), `salaryMin`/`salaryMax` (Phase 5, `Int?`), `openings` (Phase 5, `Int? @default(1)`), `district`, `address`, `status` (`JobStatus`, Phase 5 — the authoritative status), `isActive` (kept in sync with `status` — `true` iff `status === ACTIVE` — as a derived convenience so the ~8 existing public-listing queries filtering on `isActive: true` didn't need to change), `isFeatured`, `deadline` (Phase 5, renamed from `expiresAt` — nothing outside `job.controller.js` itself ever read `expiresAt`, while ten+ frontend files already expected `deadline`). Relations: `applications`, `savedBy`.

Phase 5 found that `experience`, `salaryMin`, `salaryMax`, `benefits`, `openings`, and a working `deadline` were all collected by the company's job-creation/edit forms but had no column to be saved into — every job ever created had silently lost this data. See `COMPANY_DASHBOARD_FLOW.md` for the full audit.

### `Application` (`applications`)
`jobId` + `job`, `userId` + `user`, `coverLetter`, `resumeUrl`, `status`, `notes`. Unique on `[jobId, userId]`.

### `SavedJob` (`saved_jobs`)
`jobId` + `job`, `userId` + `user`. Unique on `[jobId, userId]`.

### `JobSeekerProfile` (`job_seeker_profiles`), `Education`, `Experience`, `Certification`
Standard job-seeker profile tree, one profile per user, each with its own child records.

### `Resume` (`resumes`)
One resume per user (`userId` unique). `title`, `summary`, and JSON columns (`personalData`, `experience`, `education`, `skills`, `projects`, `certifications`) — flexible-shape sections, validated/normalized at the API layer rather than the DB layer (see `resume.controller.js`).

### `PasswordReset` (`password_resets`)
`userId` + `user`, `tokenHash` (unique — the raw token is never stored), `expiresAt`, `usedAt` (nullable — single-use).
